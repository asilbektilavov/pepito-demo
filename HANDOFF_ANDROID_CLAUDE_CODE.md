# Передача Android-проекта AI-агенту Claude Code

> Гайд для бэкенд-разработчика, который хочет отдать Android-приложение
> (`client-app`, Kotlin) на разработку и поддержку агенту **Claude Code**,
> не имея опыта в Android. Репозиторий живёт в **GitLab** (`git.fivetaxi.uz`).

Цель этого документа — чтобы человек, никогда не писавший под Android, смог
**руководить** агентом: ставить задачи, проверять результат и мержить, а не
разбираться в тонкостях Gradle и Jetpack. Весь код пишет агент.

---

## 0. Как это вообще работает (2 минуты чтения)

Claude Code — это агент, который:
- **читает** твой репозиторий целиком,
- **пишет и правит** код,
- **сам собирает проект и гоняет тесты** в терминале,
- **делает коммиты, ветки и Merge Request'ы** (в том числе в GitLab).

Твоя работа как «заказчика» сводится к трём вещам:
1. Один раз хорошо **подготовить репозиторий** (об этом ниже — это самое важное).
2. **Ставить задачи** человеческим языком.
3. **Проверять** результат: собралось ли, прошли ли тесты, работает ли на устройстве.

Главное правило: **чем лучше агент может сам себя проверить (собрать проект,
запустить тесты, линтер), тем меньше он галлюцинирует.** 80% успеха — это
рабочая команда сборки.

---

## 1. Два способа работать с GitLab — выбери один

У Claude Code есть **официальная интеграция с GitLab** (её поддерживает сама
GitLab). Работает и на self-managed GitLab, то есть на вашем `git.fivetaxi.uz`.
Есть два варианта использования. Не обязательно решать прямо сейчас — Claude
может спросить и настроить любой по твоему выбору.

| | **Вариант A: Локально + GitLab MCP** | **Вариант B: CI/CD `@claude`** |
|---|---|---|
| Где ставишь задачи | в терминале на своём компьютере | пишешь `@claude ...` прямо в GitLab (в issue/MR/комментарии) |
| Кто пишет код | локальный Claude Code | Claude в CI-джобе GitLab |
| Создание Merge Request | автоматически, через GitLab MCP | автоматически, из джобы |
| Сборка Android | на твоей машине (легко смотреть APK на телефоне) | в GitLab-раннере (нужен Android SDK в образе — сложнее) |
| Что нужно поставить | Claude Code + GitLab MCP/glab | `.gitlab-ci.yml` + API-ключ + раннеры + SDK в раннере |
| Кому подходит | соло-разработка, активная работа | команда, автоматизация, «фикс по комментарию из веба» |
| Стоимость | подписка Claude или API-ключ | API-ключ (по токенам) + минуты раннеров |

**Рекомендация для старта (соло-бэкендер):** начни с **Варианта A** — он проще,
ты сразу видишь собранный APK на телефоне, и MR создаются автоматически.
**Вариант B** подключишь позже, когда захочешь давать задачи прямо из веба GitLab
командой `@claude`.

Ниже — подробная настройка обоих. Читай раздел по своему выбору (или дай этот
файл своему Claude и скажи, какой вариант хочешь — он всё настроит).

## 2. ВАРИАНТ A — Локально + GitLab MCP (рекомендую для старта)

Здесь Claude Code работает в терминале на твоём компьютере, а с GitLab общается
через **GitLab MCP server** (или skill на базе `glab` CLI) — благодаря этому он
сам создаёт Merge Request'ы, читает issue и логи пайплайнов, не выходя из терминала.

### 2.1 Что скачать один раз
1. **Node.js** — чтобы установить сам Claude Code.
2. **Android Studio** — самый простой способ разом получить **JDK + Android SDK + эмулятор**
   (открывать её руками почти не придётся, она нужна как «набор инструментов»).
3. **Claude Code**:
   ```bash
   npm install -g @anthropic-ai/claude-code
   ```
4. **glab** (GitLab CLI) — опционально, для MR/CI через терминал:
   - Mac: `brew install glab`
   - иначе — скачать с https://gitlab.com/gitlab-org/cli/-/releases

### 2.2 Подключить GitLab
1. В GitLab создать **Personal Access Token** (Settings → Access Tokens) со scope `api`.
2. Залогинить glab в ваш self-managed GitLab:
   ```bash
   glab auth login --hostname git.fivetaxi.uz
   ```
   (вставить токен, когда попросит).
3. Подключить **GitLab MCP server** к Claude Code — самое простое: попросить об
   этом самого Клода: *«подключи GitLab MCP server для git.fivetaxi.uz, вот мой токен»*.
   Он добавит MCP-сервер в конфигурацию. После этого у Клода появятся инструменты
   вроде `create_merge_request`, чтения issue и пайплайнов.

### 2.3 Клонировать проект и запустить
```bash
git clone https://git.fivetaxi.uz/fivetaxi/frontend/client-app.git
cd client-app
claude
```
Первая задача Клоду: *«изучи проект и убедись, что он собирается (`./gradlew
assembleDebug`); если нет — почини»*.

### 2.4 Как выглядит рабочий цикл
1. Пишешь задачу в терминале человеческим языком.
2. Клод пишет код, собирает, гоняет тесты, коммитит в отдельную ветку.
3. Клод сам создаёт Merge Request в GitLab (через MCP/glab).
4. Ты проверяешь (см. раздел 5) и мержишь MR.

## 3. ВАРИАНТ B — CI/CD `@claude` прямо в GitLab

Здесь Claude запускается **внутри GitLab CI/CD**. Ты пишешь `@claude ...` в
комментарии к issue, merge request или review-треду — Claude в изолированной
джобе читает контекст, пишет код в ветку и **сам открывает Merge Request**.
Всё крутится на ваших раннерах, с вашими approvals и защитой веток.

> Статус: официальная интеграция от GitLab, в бете. Работает на self-managed.

### 3.1 Что нужно
- Рабочие **GitLab Runners** в проекте.
- **API-ключ Anthropic** (`ANTHROPIC_API_KEY`) — оплата по токенам. Альтернатива
  для энтерпрайза: AWS Bedrock или Google Vertex (через OIDC, без статичных ключей).
- Право добавить `.gitlab-ci.yml` в репозиторий.
- **Android SDK в образе раннера** — иначе сборка APK в CI не пройдёт (см. 3.4).

### 3.2 Настройка (быстрый старт)
1. **Добавить секретную переменную:** Settings → CI/CD → Variables → добавить
   `ANTHROPIC_API_KEY` (masked, при необходимости protected).
2. **Добавить job в `.gitlab-ci.yml`:**
   ```yaml
   stages:
     - ai

   claude:
     stage: ai
     image: node:24-alpine3.21
     rules:
       - if: '$CI_PIPELINE_SOURCE == "web"'
       - if: '$CI_PIPELINE_SOURCE == "merge_request_event"'
     variables:
       GIT_STRATEGY: fetch
     before_script:
       - apk update
       - apk add --no-cache git curl bash
       - curl -fsSL https://claude.ai/install.sh | bash
       - export PATH="$HOME/.local/bin:$PATH"
     script:
       - /bin/gitlab-mcp-server || true
       - >
         claude
         -p "${AI_FLOW_INPUT:-'Review this MR and implement the requested changes'}"
         --permission-mode acceptEdits
         --allowedTools "Bash Read Edit Write mcp__gitlab"
         --debug
   ```
3. **Проверить:** запустить джобу вручную (CI/CD → Pipelines) или из MR.
4. **(Опционально) Включить триггер по `@claude`:** добавить webhook на события
   "Comments (notes)", чтобы при комментарии с `@claude` дёргался pipeline с
   переменными `AI_FLOW_INPUT` / `AI_FLOW_CONTEXT`.

### 3.3 Как этим пользоваться
Просто пишешь в issue или MR:
```
@claude реализуй эту фичу по описанию задачи
@claude почини TypeError на экране профиля
@claude предложи, как закешировать ответ этого API
```
Claude анализирует код, вносит изменения в ветку и открывает/обновляет MR.

### 3.4 Важный нюанс для Android в CI
Базовый образ `node:24-alpine` **не содержит Android SDK** — сборка Kotlin/Android
там не пройдёт. Варианты:
- взять образ с предустановленным Android SDK (например, на базе
  `androidsdk/android-*` или свой Docker-образ) и в нём ставить Claude Code;
- либо добавить в `before_script` установку JDK 17 + `cmdline-tools` + нужные
  `platforms`/`build-tools`.

Это разовая настройка образа раннера. Если не уверен — дай задачу Клоду в
Варианте A: *«подготовь Docker-образ и `.gitlab-ci.yml` job для сборки нашего
Android-проекта в CI»*.

### 3.5 Стоимость и безопасность
- Тратятся **минуты раннеров** + **токены API** (зависит от размера задачи и кода).
- Оптимизация: конкретные команды `@claude`, флаги `--max-turns`, `timeout: 30m`.
- **Никогда не коммитить API-ключи** — только через CI/CD Variables (masked).
- MR от Клода ревьюишь как обычного контрибьютора.

## 4. Подготовка репозитория — обязательно для ОБОИХ вариантов

Положи в **корень репозитория** файл `CLAUDE.md`. Агент читает его автоматически
в начале каждой сессии (и в терминале, и в CI). Это «постоянная память» проекта.
Готовый шаблон — в разделе 8.

Что там должно быть:
- как собрать проект **одной командой**;
- как запустить тесты и линтер;
- структура модулей (где экраны, сеть, модели);
- стек и архитектура (MVVM? Compose или XML? Hilt? Retrofit?);
- договорённости и код-стайл;
- чего **нельзя** делать (не трогать `signingConfig`, не коммитить ключи).

## 5. Android-окружение (чтобы агент мог собирать проект)

Нужны три вещи (для Варианта A — на твоей машине, для Варианта B — в образе раннера):

- **JDK 17** — проверить `java -version`.
- **Android SDK** — переменная `ANDROID_HOME` или `local.properties` с `sdk.dir=...`.
  Компоненты: `platform-tools`, `platforms;android-XX`, `build-tools;XX.X.X`
  (версии агент возьмёт из `build.gradle`).
- **Gradle** — ставить не надо, в проекте есть `./gradlew` (сам скачает нужную версию).

Ключевые команды (их использует агент для самопроверки):
```bash
./gradlew assembleDebug        # собрать debug-APK
./gradlew testDebugUnitTest    # unit-тесты
./gradlew lint                 # анализатор Android
./gradlew ktlintCheck          # код-стайл (если подключён ktlint)
```

**«Золотая» проверка:** прежде чем давать фичи, убедись, что проект собирается
чистой командой `./gradlew assembleDebug`. Если падает — первой задачей попроси
Клода починить сборку.

## 6. Как ставить задачи и проверять результат

### Ставить задачи (человеческим языком, но конкретно)
Плохо: «сделай экран профиля красивее».
Хорошо:
> На экране профиля (`ProfileScreen`) добавь кнопку «Выйти». По нажатию — очистить
> токен через `AuthRepository.logout()` и перейти на экран логина. Стиль как у
> остальных кнопок. Убедись, что `./gradlew assembleDebug` и unit-тесты проходят.

Приёмы: ссылайся на существующее («сделай как на экране заказа»), проси план до
кода для крупных задач, всегда добавляй критерий готовности, одна задача = один запрос.

### Проверять результат (без знания Kotlin)
1. **Собралось ли:** `BUILD SUCCESSFUL` в выводе `./gradlew assembleDebug`.
2. **Тесты:** `./gradlew testDebugUnitTest` → `BUILD SUCCESSFUL`.
3. **Глазами на устройстве:** APK лежит в `app/build/outputs/apk/debug/app-debug.apk`.
   Установить: `adb install -r app/build/outputs/apk/debug/app-debug.apk`
   (телефон в режиме разработчика + USB-отладка), либо через эмулятор Android Studio.
4. **Summary агента:** Клод в конце пишет, что поменял — этого хватает для ревью
   на уровне «то ли сделал, что просил».

Если не так — просто напиши «вот это не работает, вижу такое», Клод доправит.

## 7. Частые грабли (Android + AI-агент)

- **Секреты и ключи.** `keystore` для подписи релиза, API-ключи (карты, пуши) —
  **нельзя** коммитить. Держать в `local.properties` / переменных / CI-секретах.
- **Версии SDK.** Не давай агенту «на всякий случай» поднимать `compileSdk`,
  `minSdk`, версии Gradle/Kotlin — это ломает сборку. Обновление версий — отдельная задача.
- **Долгая первая сборка.** Первый `./gradlew` качает зависимости несколько минут — это норма.
- **UI-тесты (инструментальные)** требуют эмулятора/устройства; в CI обычно не гоняют.
  Полагайся на unit-тесты + ручную проверку APK.
- **Не проси «отрефакторить весь проект» одним запросом** — дели на маленькие шаги.

## 8. Шаблон `CLAUDE.md` (скопируй в корень репозитория и заполни)

```markdown
# CLAUDE.md — правила проекта client-app

## О проекте
Android-клиент такси FiveTaxi. Язык: Kotlin.
UI: <Jetpack Compose | XML-верстка>.
Архитектура: <MVVM | MVI | Clean Architecture>.

## Стек и библиотеки
- DI: <Hilt | Koin | нет>
- Сеть: <Retrofit + OkHttp | Ktor>
- Асинхронность: Kotlin Coroutines + Flow
- Навигация: <Navigation Compose | Jetpack Navigation | своя>
- Локальное хранилище: <Room | DataStore | SharedPreferences>

## Как собрать и проверить (ОБЯЗАТЕЛЬНО запускать перед "готово")
```bash
./gradlew assembleDebug        # сборка
./gradlew testDebugUnitTest    # unit-тесты
./gradlew lint                 # анализатор
./gradlew ktlintCheck          # код-стайл (если есть)
```
Готовый APK: app/build/outputs/apk/debug/app-debug.apk

## Требования к окружению
- JDK 17
- Android SDK, compileSdk = <XX>, minSdk = <XX>

## Структура модулей
- app/ — точка входа, экраны
- data/ — репозитории, сеть, модели API
- domain/ — бизнес-логика, use-case'ы
- (опиши реальную структуру своего проекта)

## Договорённости
- Каждую задачу — в отдельной ветке feature/* или fix/*.
- Не пушить в main/master/dev напрямую, только через Merge Request.
- Следовать существующему стилю кода и именованию.

## ЧЕГО НЕЛЬЗЯ ДЕЛАТЬ
- Не коммитить keystore, API-ключи, пароли, .env, local.properties.
- Не менять compileSdk/minSdk/versionCode/versionName без отдельной задачи.
- Не менять signingConfig и конфигурацию релизной подписи.
- Не удалять существующие тесты, чтобы "сборка прошла".
```
